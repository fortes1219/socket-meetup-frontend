Socket 即時資料治理

這不是 K 線圖 demo，也不是聊天室 WebSocket demo。這場在講多分頁、高頻資料、交易操作與 Admin CRUD 更新中，前端如何治理 realtime ownership、control plane 與 refetch storm。

一句話

BroadcastChannel 不是行情資料匯流排

它是分頁之間協調 realtime ownership 的 control plane。K 線 tick 不進 BroadcastChannel；只有 leader election、release、invalidation、snapshot、sync request 這類 control message 會跨分頁。

今天要記住：前端不是只有畫 UI。每個 client 都會製造連線、流量、request、render 與記憶體成本。

這場不是什麼

不是要你把所有 Vue 專案都寫成這樣

不是一般 CRUD 教學

如果你現在只做一般後台、表單、列表，這不是明天照抄的模式。

是高併發問題定義

如果你未來碰到高頻資料、多人在線、多分頁、多裝置、金融交易或即時操作，這些問題會變成系統成本。

Realtime owner

有資格直接連 `/quote`、接收 realtime K 線 tick 的分頁。

Data plane

高頻資料通道，例如 Binance kline tick → backend `/quote` → leader tab。

Control plane

低頻協調通道，例如 leader election、`callUpdate`、snapshot、jitter refetch。

前後端責任切分

不是純 frontend mock

Backend `/quote`

高頻 K 線 data plane，依 room 推送 realtime tick。

Backend `/`

低頻 control signal，CRUD commit 後 emit `callUpdate`。

Backend REST history

提供已收線、可追溯的 K 線 history。

Backend Admin API

strict validation、transaction、audit、commit 後 emit invalidation。

Frontend BroadcastChannel

只做 tab coordination，不傳 K 線 tick。

TanStack Query

管理 server state：trading-pairs REST data。

Pinia

管理 client coordination：leader role、socket state、subscription intent。

Baseline

每個分頁都連 socket，成本會線性放大

每個被打開的分頁都是一套完整 runtime：Vue app、Pinia、TanStack Query observer、Socket.IO client、klinecharts、watch / computed / render pipeline。

  • 多一條 realtime stream，不只是多一條 socket。
  • 每筆 tick 後面還有 parse、validation、normalize、store update、chart callback、render scheduling、GC。
  • 高流量場景下，每個 client 都是成本來源。

Tradeoff

不是只有一種最佳解

每頁都連 socket

最簡單，但後端 fan-out 與前端更新成本線性膨脹。

Ticker bus

Socket 數少，但 tick 仍要 fan-out 到所有分頁，背景 UI 仍可能消耗。

SharedWorker

可以中心化 socket，但有舊 iOS / Safari 支援、port reconnect、worker recovery 等 tradeoff。

Realtime owner

控制誰能直接吃 realtime。Demo 用 1 個 owner；production 應由 backend policy 決定 quota。

上面的 31% 是對 naive per-tab baseline 算的。對 ticker bus / SharedWorker，realtime owner 贏的不是 socket 數，而是 follower 不跑 market tick 的 render pipeline，以及交易操作頁不吃二手 tick。

Leader / Follower

誰有資格 realtime，要被治理

  1. 同 origin 分頁透過 BroadcastChannel 協調 realtime owner。
  2. Leader 才連 `/quote` 並 subscribe 當前交易對。
  3. Follower 可以看 history，但不吃 realtime tick。
  4. 需要操作的分頁可重新取得 realtime ownership。
  5. 新 owner 取得權限後：reload history + reconnect socket + resubscribe。
單一分頁短暫離焦不應該粗暴斷線。DevTools、切視窗、查資料都不該讓 socket 無故抖動。handoff 應該是有其他可見操作頁要求 realtime ownership 時發生。

K 線資料

History 走 REST，realtime 走 socket

Frontend

  • `getBars` 從 REST 拿 history。
  • `subscribeBar` 從 `/quote` 收 realtime tick。
  • klinecharts same timestamp 是 overwrite，不是 append duplicate。
  • resume 時 reload history，避免資料斷層。

Backend

  • unclosed tick → emit to `/quote`。
  • closed kline → upsert DB，成為 history。
  • wire 金額用 string，避免 JS number 破壞精度。

Refetch storm

Jitter 省的是尖峰 QPS

No jitter:
1 admin CRUD → N realtime owners refetch at the same time
peak ≈ N QPS

With jitter window W:
peak ≈ N / W QPS
ownerswindownaive peakjitter peak
10,000example 10s10,000 QPS1,000 QPS
100,000example 10s100,000 QPS10,000 QPS
800,000example 10s800,000 QPS80,000 QPS

Dedupe 解同一瀏覽器內重複排隊；jitter 解跨使用者同時 refetch 的尖峰。表格的 10s 是公式示意值；demo 實作的 throttle window 約 2-6s，為了現場反應速度較短。Production 應依 resource 風險與可接受延遲調整 W。總 request 數不會憑空消失。

Admin CRUD

commit 後才 emit `callUpdate`

  1. Admin 呼叫 POST / PATCH / DELETE。
  2. Backend strict validation。
  3. DB transaction + audit。
  4. commit 成功。
  5. Backend emit `callUpdate({ resource: 'trading-pairs' })`。
  6. Frontend 立刻 invalidation，network refetch 才 jitter。
`callUpdate` 是 committed invalidation signal，不是資料本體，也不是 optimistic event。

誠實邊界

Demo 沒有下單 UI

這個 demo 沒有實作 fail-safe trading lock。它只展示 immediate invalidation 與 throttled refetch 的分層。Production 若有下單、槓桿、止盈止損，local invalidation 應先鎖交易操作，真正 enforcement 必須在 server order API。

Production policy

`maxRealtimeOwners = 1` 是 demo policy

mobile user: maxRealtimeOwners = 1
desktop user: maxRealtimeOwners = 3 或 5
professional trader: maxRealtimeOwners = 10

真正產品不應硬鎖死一個，也不該讓所有分頁無限制連線。前端要有 coordination 能力，後端要有 policy 能力。

AI workflow

AI-assisted，不是 AI-validated

這個 demo 用 AI 加速實作，但不讓 AI 自己放行 correctness。流程裡保留 contract、rules、handoff、review gate、delivery evidence、not-run / pending notes。

Q&A 快速版

容易被問的問題

Junior 聽得懂嗎？

可以聽懂問題，但不一定立刻用到。先記住：前端也會製造系統成本。

為什麼不用 SharedWorker？

可以，但它不是免費解。舊 iOS / Safari 支援度、port reconnect、subscription cleanup、worker recovery、資料仍要分發到每個分頁，都是 tradeoff。

為什麼不把 tick 用 BroadcastChannel 發給其他分頁？

那會把問題從後端 fan-out 變成前端 fan-out。交易操作頁也不應依賴其他分頁 parse 後 structured clone 過來的二手 tick。

如果真的多螢幕看多幣種？

這是合理需求，但應由 backend policy 決定 maxRealtimeOwners，例如手機 1、桌機 3 到 5、專業帳號 10。

trading-pairs 可以 CDN cache 嗎？

展示 metadata 可以 cache；tradeable、halt、suspension、session close 這類狀態不能只靠 TTL。需要 push invalidation 讓 client 先進保守狀態，再 refetch authoritative snapshot。

commit 成功但 broadcast 失敗怎麼辦？

不能叫前端重送 mutation，因為 DB 已經 commit。正確語意是 client refetch 或等待下一次 sync。

為什麼 closed K 線才落 DB？

未收線 tick 是 presentation realtime。收線 K 線才是可持久化 history，resume 時 REST history 才有穩定語意。
