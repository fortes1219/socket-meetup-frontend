Socket 即時資料治理

這不是 K 線圖 demo，也不是聊天室 WebSocket demo。這場在講多分頁、高頻資料與交易操作頁中，前端如何治理 realtime ownership。

先懂主軸 Demo 看什麼 Q&A

一句話

BroadcastChannel 不是行情資料匯流排

它是分頁之間協調 realtime ownership 的 control plane。K 線 tick 不進 BroadcastChannel；只有 control message 會跨分頁。

Realtime owner

有資格直接連 `/quote`、接收 realtime K 線 tick 的分頁。

Data plane

高頻資料通道，例如 Binance kline tick → backend `/quote` → leader tab。

Control plane

低頻協調通道，例如 leader election、callUpdate、snapshot、jitter refetch。

Baseline

每個分頁都連 socket，成本會線性放大

每個被打開的分頁都是一套完整 runtime：Vue app、Pinia、TanStack Query observer、Socket.IO client、klinecharts、watch / computed / render pipeline。

  • 多一條 realtime stream，不只是多一條 socket。
  • 每筆 tick 後面還有 parse、validation、normalize、store update、chart callback、render scheduling、GC。
  • 高流量場景下，每個 client 都是成本來源。

Tradeoff

不是只有一種最佳解

每頁都連 socket

最簡單，但後端 fan-out 與前端更新成本線性膨脹。

Ticker bus / SharedWorker

可以降低 socket 數，但仍要把 tick 分發到每個分頁，背景分頁仍可能更新 store / chart。

Realtime owner

控制誰能直接吃 realtime。Demo 用 1 個 owner；production 應由 backend policy 決定 quota。

事件流

Data plane 與 control plane 分離

  1. K 線 tick：Backend `/quote` 只推給 realtime owner，更新圖表。
  2. Admin CRUD：Backend commit 後 emit `callUpdate`。
  3. Local invalidation：前端立刻標記 resource stale，不打 API。
  4. Network refetch：會打 API 的 authoritative snapshot 才做 jitter。
  5. BroadcastChannel：只傳 control message，不傳 K 線 tick。

Refetch storm

Jitter 省的是尖峰 QPS

No jitter:
1 admin CRUD → N realtime owners refetch at the same time
peak ≈ N QPS

With jitter window W:
peak ≈ N / W QPS

Follower 不開 realtime socket；需要操作時重新取得 realtime owner。

Admin mutation commit 後 `callUpdate`，Home 經 control coordinator 與 jitter refetch 更新。

誠實邊界

Demo 沒有下單 UI

這個 demo 沒有實作 fail-safe trading lock。它只展示 immediate invalidation 與 throttled refetch 的分層。Production 若有下單、槓桿、止盈止損，local invalidation 應先鎖交易操作，真正 enforcement 必須在 server order API。

Q&A 快速版

容易被問的問題

為什麼不用 SharedWorker？

可以，但它不是免費解。舊 iOS / Safari 支援度、port reconnect、subscription cleanup、worker recovery、資料仍要分發到每個分頁，都是 tradeoff。

為什麼不把 tick 用 BroadcastChannel 發給其他分頁？

那會把問題從後端 fan-out 變成前端 fan-out。交易操作頁也不應依賴其他分頁 parse 後 structured clone 過來的二手 tick。

如果真的多螢幕看多幣種？

這是合理需求，但應由 backend policy 決定 maxRealtimeOwners，例如手機 1、桌機 3 到 5、專業帳號 10。

trading-pairs 可以 CDN cache 嗎？

展示 metadata 可以 cache；tradeable、halt、suspension、session close 這類狀態不能只靠 TTL。需要 push invalidation 讓 client 先進保守狀態，再 refetch authoritative snapshot。
